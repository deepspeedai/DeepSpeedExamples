How rdsp trains one model on many differently shaped GPU groups

rdsp cuts a model into pipeline stages. Each stage is its own small DeepSpeed training job, with its own GPU count and its own parallel layout. One CPU process (the driver) gives every GPU its work through Ray. Each stage runs the Hugging Face model's own code; nothing is converted.

  1. What problem it solvesThe parts of a vision-language model do very different amounts of work. rdsp lets each part get the GPUs and the layout it needs, on cheap GPUs without NVLink, straight from the Hugging Face checkpoint.
  2. How it does against NVIDIA's systemsEqual work, Qwen3.5-9B, 8× H100: 20%, 16% and 9% faster than Megatron-Bridge; 4% faster and even against MegatronMIMO. At 27B it was the only one of the three to fit the vision encoder on its own GPU (3-step fit check).
  3. Where it falls shortIts wins come from less CPU overhead, not faster GPU kernels. The cut estimate assumes GPUs scale linearly, so at 27B one stage idled ≈ 70% of the step. Losing one worker restarts every stage. Validated on one 8-GPU node only. Uneven GPU counts per stage have not paid off yet.
  • Read top to bottom: the sections follow the order in which rdsp builds and runs a pipeline.
  • Two parts are interactive: the schedule simulator and the layout explorer. Both use the same rules as the rdsp code.
  • Code references look like coordinator.py:250. All paths are inside rdsp/src/ray_deepspeed_pipeline/ unless they start with another folder.
1 · The problem

A vision-language model is not a stack of equal layers

The usual pipeline tools give every stage the same shape. By default they give each stage about the same number of layers, and every language stage the same GPU count and tensor-parallel width. In a vision-language model, the parts are not equal, so one stage does more work and the other stages wait for it.

Why a pipeline, and why on cheap GPUs

There are 3 standard ways to put one model on many GPUs. Tensor parallelism (TP) cuts every weight matrix into pieces, so the GPUs must add their partial results after every layer. Pipeline parallelism (PP) cuts the model by depth, so only one activation crosses each cut, once per microbatch. Data parallelism (DP) copies the model and averages gradients once per step.

What rdsp sets out to do

Give each part its own GPUs and layout

Every stage sets its own GPU count, TP, DP, sequence parallelism, expert parallelism, ZeRO stage, recompute and offload. The vision encoder can share the first stage, have a stage of its own, or run as a copy on every GPU.

Cut where the work is equal, automatically

The default cut is computed from the model and the first batch, in milliseconds, with no trial runs. It counts the vision encoder and the output layer, and it divides each stage's work by its GPU count.

Use the Hugging Face model as it is

No re-written model and no checkpoint conversion. Stages run the model's own forward (Llama, Qwen3 and Qwen3-MoE text models use a short rdsp loop over the HF layers). Given weights=, each GPU reads only its own tensors from the safetensors files. 24 model families match the unsplit model's loss.

Leave DeepSpeed and Ray as shipped

rdsp is a separate package. DeepSpeed is pinned at one commit (53a2ac44) and installed unmodified. Each stage calls the normal deepspeed.initialize(), and your call looks the same. At run time rdsp does reach into a few DeepSpeed internals (see Verdict).

The idea comes from Anyscale's “disaggregated hybrid parallelism” example (ray-project/multimodal-training), which ran a vision stage and a language stage as two Ray actor groups. rdsp makes it general: any number of stages, any layout per stage, any Hugging Face model, set by a config. The target, set by the project lead, is a PyTorch blog post on vision-language models at about 30B parameters on GPUs without NVLink.

2 · At a glance

One CPU driver, one Ray actor per GPU, one DeepSpeed job per stage

The driver plans the work and hands out the data; it holds no weights, activations or gradients. Each GPU is a Ray actor that runs a stock DeepSpeed engine on its stage's slice of the model. Activations and gradients go from GPU to GPU over NCCL. Only losses and status flags come back to the driver.

Terms on this page

Stage
A run of consecutive model layers, together with the GPUs that train it. The first stage can also hold the vision encoder; the last stage holds the loss.
Driver
The one CPU process that plans each step and gives every GPU its work. It holds no weights when the model is an empty skeleton passed with weights=, as in train_vl.py.
Ray actor
A long-lived process that Ray starts on a chosen GPU. The driver calls its methods remotely, like calling an object in another process.
NCCL
NVIDIA's library that moves tensors between GPUs, over NVLink or PCIe. A group is a set of GPUs that talk through it.
Stage worker
The Ray actor that owns one GPU and trains that GPU's part of one stage.
Stage world
The torch.distributed group of one stage's GPUs. TP and DP happen inside it. It does not know other stages exist.
Cut
How many decoder layers each stage holds, in stage order, for example 13 | 19.
Microbatch
The group of rows that moves through the pipeline as one unit. A step is many microbatches; their gradients add up before one optimizer update.
Job list
The ordered forwards and backwards one stage runs in one step, delivered in a single call.
1F1B
“One forward, one backward”: a few warm-up forwards, then each forward is followed by one backward. It keeps few activations in memory.
Bubble
The share of a step in which a stage sits idle, waiting for a neighbour.
Apply
The optimizer update at the end of a step. It starts only after every stage has finished all its backwards.
TP · DP · SP · EP
Tensor, data, sequence and expert parallelism: split each matrix, copy the stage, split the sequence, split the experts. In rdsp each is chosen per stage.
ZeRO-1
DP copies split the optimizer state (fp32 master weights and Adam moments) between them, so each keeps only its share.
Equal-work comparison
Both systems compute exactly the same token positions: same rows, same order, same padding. Only then is a time difference about the system.
Shared first stage · vision-only stage · replicated encoder
The 3 places rdsp can put the vision encoder: ahead of the first decoder layers, on a stage of its own, or as a copy on every GPU.
3 · Code map

23 modules in 4 layers, 5,349 lines

Work flows left to right. The planning layer turns your config into a frozen plan, plain data, before any actor exists. The driver runs steps from that plan. Each actor gets its slice of the plan, the stage module the driver cut from your model, and, on the last stage, your loss function.

Rule 1

The plan is plain data

plan.py, config.py, protocols.py and support_matrix.py import no torch, Ray or DeepSpeed; a test reads their import lines to make sure. The plan turns into canonical JSON with a sha256 hash, and the runtime reads nothing else.

Rule 2

Importing rdsp starts nothing

import ray_deepspeed_pipeline does not import Ray or DeepSpeed. Ray loads only when initialize() starts the actors, and DeepSpeed only inside the actors. A test runs the import in a fresh process to prove it.

Rule 3

No Ray objects leak out

Ray's object references stay inside stage_group.py. You get floats and tensors back, never a Ray future. A contract test checks this.

4 · Planning

Every decision is made, and checked, before a GPU is touched

rdsp.initialize() turns your config into a frozen plan in one function, compiler.lower(). The plan says where each layer goes, how each stage's GPUs are arranged, what each stage's DeepSpeed config is, and how tensors change shape between stages. A wrong layout fails here, in seconds, with a sentence that says how to fix it.

What lower() works out

  1. The microbatch count. From PipelineConfig.microbatches or DeepSpeed's gradient_accumulation_steps; if both are set they must agree (compiler.py:28).

  2. The cut. partition_parameters() finds the longest list of same-class blocks (the decoder layers; a vision encoder's blocks are never cut), applies the cut rule and gives every parameter name to exactly one stage. Things before the layers go to the first stage, things after them to the last (partition.py:216).

  3. Each stage's grid. num_gpus = dp × sp × tp, with dp derived. Ranks are numbered TP-fastest, so neighbouring GPUs form a TP group, as in DeepSpeed and Megatron (boundary.py:46).

  4. Each stage's own DeepSpeed config. Your config, with the per-GPU microbatch set to rows / dp, gradient clipping forced to 0, and the stage's ZeRO, TP, SP, EP and offload settings written in (compiler.py:64).

  5. The conversion on every edge. From the two stages' grids: identity, replicate-to-shard, shard-to-replicate or shard-to-shard (boundary.py:156). You can state the one you expect with ConnectionOverride; a mismatch is an error.

5 · Building a stage

Every stage runs the whole model's own forward, with most of it switched off

rdsp does not rewrite the model for each stage. A stage is a copy of the full Hugging Face module tree in which every block the stage does not own just passes its input through. Calling the model then runs its own setup code (masks, positions, rotary tables, image merge) and only the stage's own layers. This is why 24 model families work without model-specific code (hf_stage.py).

Weights

Each stage reads only its own tensors

The driver builds the model under accelerate.init_empty_weights(): shapes only, no memory. When an actor starts, load_meta_parameters() opens the safetensors index and reads just the tensors its stage owns. For a checkpoint with tied weights (Qwen3-VL-2B stores no separate output layer), the untied copy is read from the tensor it was tied to (hf_stage.py:419).

Stand-ins

Unowned modules cost nothing

The stage copy is made with copy.deepcopy(model, memo), where the memo maps every unowned block to a pass-through and every unowned module to a stand-in with meta-device tensors. So the copy never duplicates other stages' weights, and code that asks a module for its dtype or shape still works (hf_stage.py:294).

Which builder

Three builders, picked from the model

Llama, Qwen3 and Qwen3-MoE use a small hand-written CausalLMStage, GPU-checked in every layout. Any other model with an HF config uses HFModelStage above. Plain sequential models chain their parts (partition.py:455).

Limit

Where this trick stops

Weights tied across two stages are refused. Qwen3-VL feeds image features into its first decoder blocks, so its first cut must come after them and its encoder cannot be replicated. The “longest block list” rule skips the vision encoder only if it is named visual, vision_tower or vision_model.

What the stage's DeepSpeed engine gets

Each GPU calls deepspeed.initialize() on its stage module inside its own stage world. Before that, rdsp adjusts a few things (deepspeed_adapter.py:209):

6 · One training step

Two Ray calls per GPU per step, whatever the microbatch count

Each GPU gets its whole job list for the step in one call, then runs it alone. The stages pass tensors directly to each other. When every GPU reports “ready”, the driver sends one more call to each GPU: apply the optimizer update. That is all the driver does during a step.

Try it: the 1F1B job lists and the bubble

This simulator uses rdsp's own job-list rule (schedule.py:18): stage s of N runs min(N−1−s, M) warm-up forwards, then alternates one forward and one backward, then finishes the backwards. A backward takes twice as long as a forward. Move the sliders to see the idle share fall as the microbatch count grows, and rise when one stage has more work.

Units: one forward of a stage with equal work = 1. Real steps also pay for sends, the vision encoder's start-up and the apply. With equal stages the idle share is (N−1)/(M+N−1): 1/33 ≈ 3% at 2 stages × 32 microbatches; the TP4 × PP2 runs use 64, so 1/65 ≈ 1.5%. Measured steps idle more: on the 2B vision-only layout stage 1 waited ≈ 11.5% of the step, and on 4B TP4 × PP2 on H100 stage 1 waited 26%, because that cut was off.

Inside one forward and one backward on a GPU

Losses

Labels go only to the last stage

Autograd graphs cannot leave their process, so the GPU that ran a forward runs its backward. The loss is computed on the last stage, and only a float per microbatch returns to the driver.

Token-mean loss

The final weight is known before the step

The driver counts the step's answer tokens from the labels and sends that count along with the last stage's work. Each last-stage GPU multiplies its summed loss by dp × M / tokens, so after DeepSpeed's averaging every backward already carries the right weight. This equals Megatron's per-token loss.

Memory

At most N − s microbatches in flight

Stage s keeps layer activations for at most min(N − s, M) microbatches, so that part depends on pipeline depth, not on M. Its sent tensors still grow with M (see Between stages).

7 · Between stages

Each GPU asks only for the rows it owns

Two neighbouring stages can be arranged in completely different ways. rdsp gives every GPU a cell: its share of the microbatch's rows (and, with sequence parallelism, of the positions). A receiving GPU takes exactly the upstream cells that overlap its own, and stitches them. Nothing is ever gathered in one place (boundary.py).

Shapes

A 10-number header, once per step

Each message slot starts with a header: dtype, number of dims, up to 7 dims, number of extra tensors. When all microbatches have the same length, a header goes once per step per neighbour. With per-microbatch padding the lengths differ, so every message carries its own header (p2p.py:15).

Extras

Up to 62 named tensors ride along

Slot 0 is the hidden state, slot 1 the extras' names (once per step per neighbour), slots 2–63 the extras: rotary tables, position ids, masks, token ids. Only the hidden state carries a gradient. For Qwen3-VL-32B the extras add about 5% to the hidden state.

Cost

Sent tensors stay alive to the end of the step

Every async send keeps its tensor until end_step() (p2p.py:112). That is simple and safe, but it holds every boundary activation of the step in memory at once; the project lead flagged it and it is not yet fixed.

8 · Flexible layouts

Layouts that add up instead of multiply

In Megatron, the GPU count is a product: TP × PP × DP, one shape for every stage. In rdsp it is a sum: each stage is its own DeepSpeed job, so you add stages of any size and any shape. A stage of 1 GPU can sit next to a stage of 4, and each one picks its own tensor, data, sequence and expert parallelism.

9 · Balanced cuts

The cut is computed, not tuned

In a pipeline, every step runs at the pace of the slowest stage. --cuts balanced estimates the work of every part from the model and the first batch, then picks the split that makes the most loaded GPU as light as possible. It takes milliseconds and runs no trial steps (partition.py:165).

The cost of each part
  • A decoder layer costs its parameter count (work per token scales with it).
  • The output layer costs its parameter count, on the last stage.
  • The embedding is a table lookup: cost 0.
  • The vision encoder costs its parameter count × a ratio measured from the first batch:
ratio = Σimages patches × (1 + 2 × patches × width / layer_params)
        ÷ text positions actually computed

The second term is the encoder's attention over each image, which grows with the square of the patch count. For a receipt (≈ 3,200 patches, width 1,024) it makes the encoder ≈ 1.5× more expensive than its parameters say. Positions are counted at each microbatch's padded length, not the 2,048 maximum.

The search

Dynamic programming over all contiguous splits (partition.py:165):

  1. Minimise the largest value of stage cost ÷ stage GPU count.
  2. Among the splits that reach it, minimise the sum of squared per-GPU stage costs (stage cost ÷ GPU count), so no stage is left nearly idle.
  3. Ties go to splits whose earlier stages take more.

With --cuts 0,balanced the encoder gets a stage of its own and the decoder is balanced over the rest. ExplicitCuts (for example --cuts 16) overrides it.

Did it pick the right cut?

To check the estimate, cuts near it were timed for a few steps on 8 PCIe GPUs: every cut from 3 to 12 for 2B, a few for 4B (a check only; rdsp never runs one). In the benchmarks, rdsp always used its own cut, never a hand-picked one.

Where it misses

It assumes 4 GPUs do a stage's work 4× faster, whether they split it by TP or DP. TP does not scale that well when the CPU, not the GPU, sets the pace. 4B on 8× H100 at TP4: stage 0 (encoder + 12 layers) busy 12.1 s per step while stage 1 waited 3.2 s. 27B with stages of 4, 2 and 1 GPUs: the 1-GPU stage waited ≈ 70% of the step (figure above).

What it ignores

Communication, sequence-length effects in decoder attention, and MoE sparsity (it counts all experts, not the active ones). It measures the image ratio from the first batch only.

10 · Efficiencies

Where rdsp saves time and memory

Most of rdsp's speed comes from doing less around the GPU work. Fewer calls from the driver, data that arrives before it is needed, less padding, no 2 GB logit gathers, and memory saved so that recompute can be switched off. Each bar adds one change; the last bar adds two.

From 40% slower to 14% faster than MegatronMIMO, one change at a time

Qwen3.5-2B in MIMO's layout (vision encoder on 1 GPU, language model TP2 × DP2), 8× RTX PRO 4500 PCIe, seconds per step. Lower is better.

rdsp after the changeMegatronMIMO, 9.64 s

The same chain for 4B TP2×PP2×DP2 went 13.51 → 11.57 → 10.58 → 8.71 → 8.69 s; there, dropping recompute gave 11.57 s, freed bf16 gradients allowed a later cut (10.58 s), per-microbatch padding gave the big drop (8.71 s), and the balanced cut chose that same cut (8.69 s). (That chain starts on the second test machine; on the first, the same layout took 15.77 s, 61% slower than Bridge.) One caveat on the last bar: per-microbatch padding means rdsp computed fewer padded positions than MIMO, which pads every row to 2,048 (MIMO's own dynamic padding gave 9.60 s, so it did not help MIMO).

11 · Failures and checkpoints

A failed step either changes nothing, or locks the pipeline

No stage ever ends up on different weights from the others without rdsp knowing. Because no optimizer runs until every stage is ready, a failure inside a step leaves all weights as they were. A failure during the optimizer update is the only dangerous case, and then every call is refused until a checkpoint is loaded.

Saving

The manifest is the commit

Every GPU writes its DeepSpeed shard and its RNG state into <tag>/stage<s>/. After a barrier, each stage's first GPU takes the sha256 of every file. The driver then writes manifest.json last: plan hash, step, data position, all digests. A folder without a manifest is an unfinished save and is never loaded. Tags cannot be overwritten (checkpoint.py).

Recovery

A rebuild replaces every stage worker

If any actor is gone, load_checkpoint() kills all stages and starts them again, asking Ray for the same nodes so node-local shards can still be found. There is no single-actor replacement yet. Checkpoints on local disks survive the loss of an actor, not of a node.

How it is checked

The whole runtime runs on a laptop: Ray actors over gloo, with a small PyTorch stand-in for the DeepSpeed engine. 557 tests are collected; about 510 run without a GPU. The GPU tests use real DeepSpeed and NCCL, mostly on tiny models in fp32; one loads the real Qwen3-0.6B weights and trains in bf16.

Why SGD, not Adam, in the parity tests

Adam normalises away a uniformly wrong gradient scale: a stage that got half its true gradient still trained the same, and a deliberately broken build passed. With SGD, and a rule that each step must move the loss by at least 20× the tolerance, the tests found 4 real bugs: ZeRO-1/2 replaced each microbatch's gradient instead of adding it; Qwen3's per-head norms drifted across TP ranks; the sequence-parallel gradient scale was inverted; AutoEP folding sent one rank's partial gradient upstream. All four were fixed without touching DeepSpeed.

Where the contract is weaker than it reads
  • A crash can look like a hang. When one GPU ran out of memory in its forward pass (27B, 2026-10-12), its neighbours sat in NCCL waits and the run hung instead of raising StepFailed. Elsewhere such waits end only at the 300 s NCCL timeout.
  • “Retry is exact” needs the same data. A failed step has already taken its M microbatches from the iterator. With rdsp's own data loader or with prefetch, calling train_batch() again trains on the next M. The tests retry with a fresh iterator over the same rows.
  • Checkpoints are tied to the exact plan. The plan hash covers every stage's full DeepSpeed config, so a different cut, a different GPU count for one stage, or even a new learning rate makes a checkpoint unloadable. There is no resharding to another layout.
  • Recovery is manual. Your script must catch the error and call load_checkpoint(); train_vl.py, which ran every benchmark, never saves a checkpoint.
  • The error reported may be a neighbour's. The driver raises the first failing stage in stage order, which can be a stage that only timed out waiting; each GPU prints its own traceback at once to make up for it.

Why the MIMO layouts are close

a · vision 1 GPU + TP2 × PP2 · rdsp 4% faster

MIMO is held back by its vision GPU. That GPU computes for only 3.4 s of an 11.9 s traced step: its CPU must launch about 158,000 kernels per step. Every hand-off also reads tensor shapes back from the GPU (bridge_communicator.py:977, a .tolist()), which blocks the CPU; the first language GPU waits ≈ 44 ms per microbatch (traced) for the vision GPU to finish its forward pass. rdsp's encoder forward takes 2.3 s per step against MIMO's 4.9 s, so rdsp's limit moves to its language GPUs.

b · vision 1 GPU + TP2 × DP2 · even

Both are limited by their language GPUs. MIMO's language forward is 0.5 s slower; rdsp's language backward is 1.1 s slower (4.5 s against 3.4 s, 1.3×), and rdsp waits 0.4 s less. Net: 8.22 s against 8.11 s. A lighter backward is the open item for rdsp here.

More vision GPUs never helped MIMO: in a 15-step sweep, vision on 2 or 4 GPUs was 2–26% slower than on 1 GPU, because the encoder is limited by CPU kernel launches, not by GPU time. A profiling lesson from this work: py-spy cannot see rdsp's waits for a gradient, because they happen inside the backward pass. Both layout write-ups were corrected after Nsight showed it.

13 · Verdict

Strengths and weaknesses, with the evidence for each

rdsp's design is sound and its flexibility is real; its speed edge is smaller and more specific than the old headline said. It wins where CPU overhead decides the step and where per-stage layouts matter. It has not yet shown that uneven GPU counts pay off, and its cost model and recovery are first versions.

+ Strengths

  1. Per-stage layouts from one config. Stages of 1, 4, 2 and 1 GPUs, each with its own TP, ZeRO and recompute. At 27B this layout fit on one 8× H100 node; MegatronMIMO ran out of memory and Megatron-Bridge has no such layout.
  2. Faster than Megatron-Bridge at equal work. 20%, 16% and 9% shorter steps on 9B (three layouts); even with MegatronMIMO in its own layout.
  3. The driver stays out of the way. 2 Ray calls per GPU per step; with prefetch, handing a step to the GPUs takes ≈ 1 ms. The 8-stage pipeline ran about 2× faster without per-operation calls (measured on two different machines).
  4. Hugging Face models as they are. No conversion, no model re-write; each stage reads only its own tensors. 24 families pass against the unsplit model. First step on 9B: 26 s against Bridge's 299 s.
  5. An automatic cut that counts the encoder. Exact in 2 of 3 PCIe checks, 1 layer off in the third, computed in milliseconds.
  6. Strict correctness testing. SGD-based parity tests found 4 real gradient bugs. Real Qwen3-VL weights: pipeline loss equals the unsplit model's within 3e-8.
  7. A clear failure contract. Inside a step, a failure changes no weights; during apply, it locks the pipeline. Checkpoints commit atomically with a manifest of file digests.
  8. Memory tools. bf16 gradient buffers plus fused AdamW let 27B TP4 × PP2 fit on 80 GB GPUs without recompute (3-step check, 24.6 s/step); optimizer groups then cut the step to 22.1–22.7 s. Recompute can be set per stage.
  9. No changes to DeepSpeed or Ray. A separate package on a pinned DeepSpeed commit.

− Weaknesses

  1. The wins are on the CPU side. On the profiled layouts the GPUs sat idle most of the step on both systems. rdsp launches 1.6–2.3× more kernels, and its backward is slower (0.9 s on 9B stage 0; 1.1 s on the MIMO layout's language GPUs).
  2. The cut model counts parameters and assumes GPUs scale linearly. At 27B the 1-GPU stage idled ≈ 70% of the step; at 4B TP4 on H100 stage 1 waited 3.2 s. It ignores communication and MoE sparsity.
  3. Uneven GPU counts have not paid off yet. A 2-GPU head stage on Qwen3-0.6B ran at 0.91–0.97× of a plain extra stage; both written predictions failed.
  4. Recovery is coarse. One lost actor means rebuilding every stage from the last checkpoint. Checkpoints are node-local. A failure can take the 300 s NCCL timeout to surface, and an out-of-memory error in a forward pass hung the 27B run.
  5. Schedule and training gaps. 1F1B only (no interleaved or zero-bubble schedule), no global gradient clipping, no tied weights: every train_vl.py run trains the embedding and the output layer as two separate matrices, even when both sit on one stage. For 2B and 4B, whose checkpoints tie them, Megatron keeps them as one; 9B and 27B have a separate output layer in both systems, so the equal-work 9B results are unaffected.
  6. Boundary overheads. When DP grows across a cut, every receiving GPU gets its sender's whole cell (each TP partner its own copy). Sent tensors stay allocated until the step ends. Ragged microbatches add a host sync per message.
  7. Narrow validation. One 8-GPU node; multi-node and the 32-GPU four-stage layout never ran; one run per configuration; the 4B equal-work layouts were planned but not run.
  8. Leans on DeepSpeed internals. The docs say 2 places; a code read finds 4–6 (private ZeRO fields, an AutoTP marker, folding handles). A DeepSpeed upgrade needs the GPU suite again.
  9. Compile is fragile. The vision encoder crashed compiled under TP4 at 27B (cause unknown), so the 9B runs, with the same encoder, ran it uncompiled. Compiling Qwen3.5 decoder blocks crashed too.
Documentation that no longer matches the evidence
  • README.md's headline (“13–28% less time … with the same layouts, data and settings”) mixes in the Bridge pipeline pairs that were not equal work, and says Bridge pads to multiples of 128 (it pads pipeline runs to 2,048). The equal-work 9B results are not in the README yet.
  • The 27B conclusion and summary report still say 27B “fits only with full recompute”; the Oct 12 fit checks show both systems fit with bf16 gradient buffers.
  • Smaller drift: the docs say ≈ 430 CPU tests, ≈ 510 are collected now; the 2B speed chain's first row says the encoder shared a stage, but that run already had its own vision stage; the docs still use the word the glossary bans for the replicated encoder.
14 · Limits and next steps

What would make the case stronger

The open work falls into three groups: finish the measurements, fix the two mechanisms that limit speed today, and show the scenarios where a Ray-driven pipeline should clearly win.

Finish the measurements
  • 27B 50-step runs: Bridge and rdsp on TP4 × PP2, rdsp's 1 | TP4 | TP2 | 1 layout, TorchTitan as a third system (≈ 2.9–3.9 h).
  • Repeats for spread; the planned 4B TP2 × PP2 × DP2 and DP8 equal-work layouts.
  • rdsp's own padding as a separately labelled number, and a tuned Megatron (TP communication overlap on) as another.
Fix what limits speed
  • A cut model that uses measured time per stage, or at least TP efficiency, instead of parameters ÷ GPUs.
  • A lighter backward: fewer, fused kernels; check DeepSpeed's throughput timer, which syncs the GPU on every forward (found in the 9B profile, unmeasured).
  • Free sent tensors when their send completes; send only the rows each receiver needs.
  • Make the vision encoder compile under TP.
Show where Ray fits
  • Replace one failed actor instead of rebuilding every stage; checkpoints on shared storage so a node loss is survivable.
  • Multi-node and mixed GPU types: stages on different machines, the driver on a CPU node.
  • About 30B vision-language models on GPUs without NVLink, reported as cost per token.
  • Global-norm clipping, an interleaved schedule, and weights tied across stages.
