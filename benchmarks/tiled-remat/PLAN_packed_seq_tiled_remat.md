# Plan: packed-sequence tiled rematerialization

*Implementation plan for [WRITEUP_packed_seq_tiled_remat.md](WRITEUP_packed_seq_tiled_remat.md). Extends `TiledRematerialize` to cut sequence-mixer rematerialization workspace at physical `mbs=1` when the row is a pack of independent samples described by `cu_seqlens`.*

## Scope / non-goals

In scope: one physical row that packs several independent, whole samples end to end, with pack metadata (`cu_seqlens` or HF `cu_seq_lens_q/k`) locating every boundary. Tiling is over contiguous groups of whole packed samples, mixer submodules only (attention, GDN), matching `deepspeed/runtime/activation_checkpointing/tiled_rematerialization.py`'s own axis contract ("Use for batch-independent, sequence-mixing modules").

Out of scope, unchanged from the WRITEUP: splitting inside one sample (resets GDN recurrent/short-conv state, breaks causal attention); whole-decoder-layer wrapping (would nest a token-tiler for FFN inside this tiler and hit the known duplicate-`ds_grad_is_ready`/IPG conflict); KV/`Cache` objects (already rejected and staying rejected); `mbs>1` packed rows (each physical row still gets its own tile plan under batch-axis `TiledRematerialize`/`tiled_rematerialize_compute` if `mbs>1`, this plan does not fuse the two axes); throughput parity with batch-tiled `mbs>1` (this is a capacity claim, see Benchmark/measurement plan).

## Proposed API surface

New code lives in the same module as the existing mechanism, `deepspeed/runtime/activation_checkpointing/tiled_rematerialization.py`, as a sibling pair to `tiled_rematerialize` / `tiled_rematerialize_compute`, not a modification of them.

```python
def plan_packed_tiles(cu_seqlens, shards=None, token_budget=None):
    """Group whole samples of one packed row into contiguous tiles.

    Returns a list of (start_sample, end_sample, start_tok, end_tok) tuples,
    end-exclusive on both axes, covering every sample exactly once in order.
    Pure tensor/Python logic: no device sync beyond reading `cu_seqlens`
    (already resident), no collectives. See "Tile-planning algorithm".
    """

def rebase_cu_seqlens(cu_seqlens, start_sample, end_sample):
    """cu_seqlens[start_sample:end_sample+1] - cu_seqlens[start_sample].

    Tile-local cumulative lengths starting at 0, length (end_sample-start_sample+1).
    """

def classify_packed_kwarg(name, value, num_samples):
    """Classify a kwarg for packed-sequence tiling: reject (cache), pack_meta
    (allowlisted cu_seqlens/max_seqlen/seq_idx family, rebased per tile),
    token (sequence-major tensor sliced on the token axis), or pass (dim0==1,
    scalar, None). Distinct from `classify_rematerialize_kwarg`, which
    still hard-rejects every `cu_seqlens`-named kwarg for the batch axis."""

def packed_seq_tiled_rematerialize_compute(fn,
                                           hidden_states,
                                           cu_seqlens,
                                           shards=None,
                                           token_budget=None,
                                           compute_params=None,
                                           kwargs_to_token_shard=None,
                                           kwargs_to_pass=None,
                                           tile_forward=False,
                                           fwd_tile_size=None,
                                           fwd_shards=None):
    """Tile fn(hidden_states, **kwargs) over contiguous whole-sample tiles of
    one packed row. No-op when cu_seqlens describes a single sample."""

class PackedSeqTiledRematerializeCompute(torch.autograd.Function):
    """Token-axis analog of TiledRematerializeCompute. Tiles are whole-sample
    groups from plan_packed_tiles, not equal torch.chunk shards."""
```

Naming follows the module's existing `tiled_rematerialize` / `tiled_rematerialize_compute` split: a function-based helper plus one generic "compute" entry point that takes `fn(hidden_states, **kwargs)`. There is no `packed_seq_tiled_rematerialize(fn, module, x, ...)` counterpart to plain `tiled_rematerialize`, because every real caller needs at least `cu_seqlens` threaded through, which only the `_compute` shape supports.

**Why a new function, not a kwarg on `tiled_rematerialize_compute`** (constraint 7). `_reject_rematerialize_kwarg` (L107-118) raises `TypeError` on any kwarg whose name contains `cu_seqlens`, and `test_classify_rematerialize_kwarg` (`tests/unit/ulysses_alst/test_tiled_compute.py:428-446`) pins that behavior. Keeping that rejection on the batch-axis entry point is a safety rail: a caller who passes pack metadata into `tiled_rematerialize_compute` by mistake gets a loud `TypeError` today, not silently wrong numerics from `torch.chunk`-ing `cu_seqlens` like a batch-major tensor. An `is_packed=True` flag on the same function would have to special-case almost every branch (shard-plan source, tile-count agreement, kwarg classification, autograd Function selection) and would let that safety rail regress into a runtime `if`. A separate function name is self-documenting at every call site, matches the repo's existing two-entry-point pattern, and is the option the WRITEUP names explicitly ("specify a separate entry point or an explicit opt-in kwarg").

The mixer-only wrap for a real model needs an installer parallel to `_install_tiled_rematerialize` in `autorun/bench_qwen3_offload.py:228-316`, but pointed at the attention/GDN submodule, not the decoder layer: see "Benchmark/measurement plan".

## Tile-planning algorithm

`plan_packed_tiles(cu_seqlens, shards=None, token_budget=None)`. `cu_seqlens` is a 1-D tensor of length `N+1` for `N` samples, `cu_seqlens[0]==0`, strictly increasing. Exactly one of `shards` (target tile count) or `token_budget` (max tokens per tile) is given; if both, `token_budget` is primary and `shards` upper-bounds the tile count as a stop condition.

Greedy pass, run once per rank on data already resident (no collective, no cache):

1. If `N == 1`: return `[(0, 1, 0, cu_seqlens[1])]` — one tile, the whole row. This is the no-op path; callers must special-case it exactly like `tiled_rematerialize_compute` special-cases `batch <= 1` (L348), skipping `PackedSeqTiledRematerializeCompute.apply` entirely and calling `fn` directly.
2. Otherwise walk samples left to right, accumulating tokens into the current tile. Close the current tile and start a new one when adding the next whole sample would exceed `token_budget` AND the current tile already has at least one sample. A single sample longer than `token_budget` becomes its own one-sample tile that exceeds the budget — the budget is soft, per the WRITEUP ("A sample longer than the token budget makes the budget soft"); do not split it.
3. If `shards` was given instead of (or in addition to) `token_budget`, derive an implied token budget as `ceil(total_tokens / shards)` first, then run the same greedy walk. This mirrors `_shards_for_tile_size` (L47-50) being the dual of `_usable_shard_count` (L69-78) in the batch-axis code — a target count is converted to a size, then re-walked, rather than doing a naive `N // shards` split of the sample list (which would ignore per-sample token cost entirely and defeat the purpose of a *token* budget).

Degenerate cases:

- **Single sample.** Handled by step 1; always exactly one tile, matching "backward-compat: a pack with a single sample must remain a no-op" (constraint 7).
- **One sample larger than the budget.** Handled by step 2; that sample gets its own oversized tile. If it is also the *only* sample this degenerates to the single-sample case above.
- **Empty tiles.** Cannot occur from this walk: every step either starts a new tile with a real sample or extends the current one; a tile is closed only when non-empty. This differs from the batch-axis code, which must actively guard against a trailing empty `torch.chunk` slice (`_usable_shard_count`'s `while resolved > 1` loop, L73-77) because `ceil`-splitting a fixed row count can strand an empty tail; a sample-boundary walk never produces that shape.
- **Cross-rank disagreement.** Not resolved inside `plan_packed_tiles` — it is a pure per-rank function and deliberately does not call into `dist`. Agreement is a separate step layered on top; see below.

### Cross-rank tile-count agreement

This is the design point the WRITEUP itself flags as the single riskiest ("This is the single riskiest design point — treat it carefully"), and it cannot reuse `_agree_rematerialize_shards` (L88-104): that function's cache key is `(shards, batch, world_size)`, and batch is always `1` on this axis (one physical row), so every rank would collide on the same cache key while actually needing different tile counts for different packings — a cache hit would silently return a stale, wrong count from an earlier microstep's packing.

Decision: **agree on a token count is not the mechanism — agree on a bounded tile count, uncached, every call** (WRITEUP option (b)). Concretely:

1. Each rank computes its own greedy plan `local_tiles = plan_packed_tiles(cu_seqlens, shards, token_budget)` and takes `local_count = len(local_tiles)`.
2. All ranks `dist.all_reduce(torch.tensor(local_count), op=dist.ReduceOp.MIN)` to get `agreed_count`.
3. If `agreed_count < local_count`, the rank must *merge* its own `local_tiles` down to exactly `agreed_count` non-empty contiguous groups (never re-derive from a different budget — that could reintroduce a different local count). Merge greedily from the plan already computed: repeatedly fuse the two adjacent tiles whose combined token count is smallest, `local_count - agreed_count` times.
4. If `agreed_count == local_count`, no merge needed. `agreed_count` can never exceed `local_count` for any rank by construction of MIN, so step 3 is a shrink only, never a split — a tile is never divided into more tiles than the greedy pass judged safe, so no rank is asked to fabricate empty or single-sample-splitting tiles.

Why MIN and why this is safe: `local_count <= N_local` always (a tile needs at least one sample), so `agreed_count = min_i(local_count_i) <= local_count_k <= N_local_k` for every rank `k`. Every rank can therefore always merge down to `agreed_count` non-empty groups from its own samples — the bound the WRITEUP asks for ("a common tile count bounded by min samples across ranks") falls out automatically because `agreed_count` is already bounded by every rank's own achievable tile count, which is in turn bounded by its own sample count. No rank is ever asked to produce more tiles than it has samples for, so empty tiles stay impossible after agreement too, closing the gap the WRITEUP leaves open.

This is an **uncached** all-reduce, once per call to `packed_seq_tiled_rematerialize_compute`, i.e. once per wrapped mixer submodule per microstep — the same "L collectives, L device syncs" cost the module docstring already accepts for the batch-axis path's per-layer-per-microstep granularity (module docstring, L20-28, "ZeRO-3 compute_params are gathered at forward and again at rematerialize entry"). Caching by packing shape is not safe here (a cache keyed on anything derived from `cu_seqlens` values requires a host read of `cu_seqlens`, which is itself a device sync, defeating the purpose of caching to avoid one) so this plan does not attempt it; if profiling later shows the all-reduce matters, a same-microstep cache keyed on `id(cu_seqlens)` (the identical tensor object is threaded unchanged through every decoder layer within one forward pass) is the natural follow-up and is listed under Risks.

WRITEUP option (c) — relying on per-param IPG ordering instead of per-tile symmetry — is not adopted: it depends on ZeRO's internal reduction ordering guarantees that are not part of the public contract exercised by `_hold_gathered_params` (L169-217) or `_mark_compute_params_ready` (L220-222), and the module's own comment on `_hold_gathered_params` already shows how fragile ZeRO-3's active-submodule accounting is to small assumption breaks. Option (a) (collate so every rank shares a sample count / token budget before the forward even starts) is deferred to the data-loading layer, not this module — it would help but requires the packing/collation code, not the tiler, to change, and this plan's job is the tiler being correct for whatever packing arrives, not requiring a specific collation. Note where it lives in the pipeline: `deepspeed/runtime/sequence_parallel/ulysses_sp.py`'s `UlyssesSPDataLoaderAdapter` (L564) is the closest existing analog of a collation layer and where an (a)-style change would eventually go, but it is out of scope for this plan.

## Per-tile execution

`PackedSeqTiledRematerializeCompute.forward` mirrors `TiledRematerializeCompute.forward` (L472-538) with the chunking source swapped:

- **Layout.** `hidden_states` is `[1, T, H]` or `[T, H]`. Detect once: `token_dim = 1 if hidden_states.dim() == 3 else 0`. Every slice below uses `hidden_states.narrow(token_dim, start_tok, end_tok - start_tok)`, matching the `narrow`-based token slicing already used in `sequence_tiled_compute`/`SequenceTiledCompute` (`ulysses_sp.py:832-846` backward loop) rather than `torch.chunk`, since packed tiles are not equal-sized.
- **cu_seqlens rebasing.** Never slice `cu_seqlens` like a batch-major tensor (constraint 1 — this is exactly what `_reject_rematerialize_kwarg`, L113-115, exists to stop on the batch axis). Use `rebase_cu_seqlens(cu_seqlens, start_sample, end_sample)`: `cu_seqlens[start_sample:end_sample+1] - cu_seqlens[start_sample]`. The result starts at 0 and ends at the tile's own token count, exactly the metadata a varlen attention kernel expects for an independent call. `max_seqlen_q`/`max_seqlen_k` (or HF's `max_length_q/k`) are recomputed as `local_cu_seqlens.diff().max()` per tile, not sliced from the row's global max — the row's global max_seqlen can be larger than any one tile's, and passing it through would oversize the kernel's internal buffers for no benefit but not corrupt results; recomputing is cheap and exact.
- **Kwarg handling.** `classify_packed_kwarg` distinguishes three buckets, replacing the two-bucket (`shard`/`pass`) system of `classify_rematerialize_kwarg` (L150-159), which does not have a category for "rebase, don't slice":
  - `pack_meta` — the allowlist from the WRITEUP's "Implementation notes": `cu_seqlens`, `cu_seq_lens_q`, `cu_seq_lens_k`, `max_seqlen_q`/`k`, `max_length_q`/`k`, `seq_idx`. Rebased via `rebase_cu_seqlens`/recomputed, never sliced positionally.
  - `token` — sequence-major companions: `position_ids`, sequence-major `attention_mask`, batch-major-tuple `position_embeddings` (`cos`, `sin`) when their non-batch dim matches the token axis. Sliced with the same `narrow(token_dim, start_tok, end_tok)` as `hidden_states`.
  - `pass` — `None`, scalars, or anything whose shape does not vary with the token axis (mirrors `_classify_tensor_dim0`'s dim0==1 passthrough, L126-127, but on the token axis instead of batch).
  - Cache objects and anything not on the allowlist keep raising `TypeError`, reusing `_reject_rematerialize_kwarg`'s cache check (L111-112) unchanged — packed tiling does not relax that rule (constraint 5).
- **Output concat.** Tiles are visited in ascending sample order by construction (`plan_packed_tiles` walks left to right), so `torch.cat(output_shards, dim=token_dim)` reproduces the original sample order with no extra bookkeeping — unlike batch-axis GAS-style re-ordering concerns, there is no permutation step.
- **ZeRO param hold.** Reuse `_hold_gathered_params` (L169-217) verbatim, called once around the whole tile loop exactly as `TiledRematerializeCompute.backward` does (L566), for the same reason: `GatheredParameters(..., coalesced=True)` amortizes the allgather across tiles instead of once per tile.
- **Grad-readiness gating.** Reuse `_mark_compute_params_ready` (L220-222) verbatim: `is_last = (i + 1 == len(tiles))`, flips `ds_grad_is_ready` True only on the last tile. Because packed mixer tiling wraps the mixer submodule only and does not nest a second tiler inside its per-tile `fn` (out of scope per the Scope section), this plan does not hit the known TiledMLP-inside-TiledRematerialize duplicate-`ds_grad_is_ready`/IPG conflict the WRITEUP calls out — that conflict is specifically about nesting two tilers so that an inner last-tile and an outer last-tile both fire on the same parameter set. A sibling call — attention wrapped with this tiler, then FFN wrapped with `TiledMLP` right after in the same decoder layer forward, not one inside the other — drives disjoint parameter sets and is unaffected. If a future whole-decoder wrap is attempted, the AND-of-last-tile fix referenced in the WRITEUP becomes a hard requirement; this plan does not implement it, matching "whole-decoder wrapping" being explicitly out of scope.
- **`tile_forward`.** Same semantics as `TiledRematerializeCompute`: default first forward runs on the full packed row once (`fn(hidden_states, **kwargs)`, still the same varlen kernel shape as an unwrapped call — no padding introduced, unlike the unpack-to-`mbs=N` baseline). `tile_forward=True` chunks that first `no_grad` pass into the same tile plan (or a coarser one via `fwd_tile_size`/`fwd_shards`, resolved the same way `_resolve_forward_shards`, L53-66, resolves the batch axis's `fwd_shards`) and concatenates, for when mixer forward workspace alone already OOMs on the whole row.
- **Offload.** `_offload_remat_input`/`_load_remat_input` (L239-284) are reused unchanged; they operate on the `hidden_states` Function-input tensor regardless of what axis backward tiles over.

## Ordered, reviewable implementation steps

Each step is one commit, matching AGENTS.md's minimal-diff discipline (`AGENTS.md`, repo root).

1. **`plan_packed_tiles` + `rebase_cu_seqlens`, unit-tested, no autograd/no GPU.** File: `deepspeed/runtime/activation_checkpointing/tiled_rematerialization.py`. Add the two pure functions and nothing else — no autograd.Function, no installer, no distributed code. Test: new unit tests in `tests/unit/ulysses_alst/test_tiled_compute.py` covering single-sample, oversized-sample, and multi-sample budget/shards inputs (see Test plan). This step is reviewable purely on the tile-planning algorithm without touching any existing code path.
2. **`classify_packed_kwarg` + allowlist, unit-tested.** Same file. Add the three-bucket classifier next to `classify_rematerialize_kwarg`, explicitly not modifying `_reject_rematerialize_kwarg`/`classify_rematerialize_kwarg` themselves (that rejection must keep passing `test_classify_rematerialize_kwarg` unchanged — a regression there would break the batch-axis safety rail). Test: unit test mirroring `test_classify_rematerialize_kwarg`'s structure, one assertion per bucket plus the Cache-object and non-allowlisted-name rejections.
3. **`PackedSeqTiledRematerializeCompute` autograd Function + `packed_seq_tiled_rematerialize_compute` wrapper, single-rank only.** Same file. Wires steps 1-2 into forward/backward following `TiledRematerializeCompute`'s shape (L469-583), reusing `_hold_gathered_params`, `_mark_compute_params_ready`, `_offload_remat_input`/`_load_remat_input` unchanged. No cross-rank agreement yet — assume `world_size==1` or that all ranks already agree (defer to step 4). Test: `DistributedTest` with `world_size=1` in `tests/unit/ulysses_alst/test_tiled_compute.py`, following `TestTiledRematerialize`'s pattern (parametrized `zero_stage in [2, 3]`) — packed-vs-unpacked gradient parity on a small `SeqMix`-like module extended to accept `cu_seqlens` (a new `PackedSeqMix` test module, analogous to `SeqMix` at L367-385 but consuming `cu_seqlens`/`position_ids` instead of `mask`/`bias`), plus the single-sample no-op negative control.
4. **Cross-rank tile-count agreement.** Same file. Add the MIN-all-reduce and merge-to-`agreed_count` step from "Cross-rank tile-count agreement" above, gated the same way `_agree_rematerialize_shards` gates on `dist.is_initialized() and dist.get_world_size() > 1` (L90). Test: `DistributedTest` with `world_size=2` (mirrors `TestTiledRematerializeDistributedReduce`, L586-627) where each rank is given a different packing (different sample-length histograms) that would otherwise produce different local tile counts, asserting the loop runs `agreed_count` times on every rank and gradients match a single-rank packed-untiled reference.
5. **Docs.** `docs/_tutorials/ulysses-alst-sequence-parallelism.md`: new subsection after `#### Tiled rematerialization vs Tiled MLP` (currently ending around line 401) documenting the packed entry point, the mixer-only-wrap constraint, and the tile-count-agreement scheme; add an `mbs=1` packed row to the existing axis-comparison table. No code changes in this commit.
6. **Bench harness plumbing.** `autorun/bench_qwen3_offload.py`. New flags and a packed-input path; see Benchmark/measurement plan for exactly what is missing today. This is deliberately last: it depends on steps 1-4 existing and is the only step that needs a real model (Qwen3) and a real varlen attention path, so it is the highest-risk step to land and the one most likely to reveal gaps in the plan above (e.g. an HF kwarg name this plan's allowlist missed).

Steps 1-4 need no GPU and no model; they are self-contained additions to one file plus its test file, reviewable independently of whether the bench-harness integration (step 6) ultimately needs adjustments.

## Test plan

Mapped onto `tests/unit/ulysses_alst/test_tiled_compute.py` conventions:

- **Kwarg classification (no GPU, no distributed).** `test_classify_packed_kwarg`, next to `test_classify_rematerialize_kwarg` (L428-446): assert `pack_meta` for `cu_seqlens`/`cu_seq_lens_q`/`max_seqlen_q`/`seq_idx`, `token` for `position_ids` and sequence-major `attention_mask`, `pass` for `None`/scalar/dim0==1, and that `classify_rematerialize_kwarg` (the batch-axis one) is untouched — still raises on `cu_seqlens` (regression guard for the existing safety rail).
- **Tile planner (no GPU, no distributed).** `test_plan_packed_tiles`: table-driven over (a) single sample → one tile spanning the whole row; (b) even samples under a token budget → expected boundaries; (c) one sample exceeding the budget → its own oversized tile, budget honored elsewhere; (d) `shards` given instead of `token_budget` → same boundaries as the equivalent derived budget. `test_rebase_cu_seqlens`: a multi-sample `cu_seqlens` sliced at an interior boundary rebases to start at 0 and match the tile's own token count.
- **Distributed grad-parity, `world_size=1`.** New `class TestPackedSeqTiledRematerialize(DistributedTest)` parametrized like `TestTiledRematerialize` (`zero_stage in [2, 3]`, plus a packing-shape axis instead of `batch_size`/`shards`: e.g. `[(3 samples, budget covers 2), (1 sample, no-op), (1 sample larger than budget alone)]`). Body follows `test_tiled_rematerialize_compute_kwargs` (L521-582): build a `PackedSeqMix` module (cumsum-based sequence mixer like `SeqMix`, L367-385, but consuming rebased `cu_seqlens` to prove rebasing is actually wired through, e.g. resetting its cumsum at each rebased boundary) run once plain and once through `packed_seq_tiled_rematerialize_compute`; assert loss, `x.grad`, and parameter grad all match via `torch_assert_close`, and `_assert_compute_params_ready` (L423-425) passes after backward.
- **Packed-vs-unpacked oracle.** Construct one packed row of `N` short samples and, separately, `N` individual `mbs=1` rows through the *same* unwrapped `PackedSeqMix`/module (no packing, no tiling) with the model's ordinary un-packed forward. Assert per-sample output slices and per-sample input grads from the packed+tiled run match the corresponding unpacked run to remat tolerance (`torch_assert_close`'s default tolerance, matching every other test in the file). This is the correctness oracle from constraint 8, and it is `PackedSeqTiledRematerializeCompute` vs a genuinely different code path (no packing at all), not packed-tiled vs packed-untiled — cross-checking both is worth doing, but the WRITEUP explicitly marks the unpacked-`mbs=N` comparison secondary ("different kernels, pad, possible GDN-conv numerics"), so this oracle test should tolerate a looser bound than the packed-tiled-vs-packed-untiled parity test above, and should not gate merge if a model's real varlen kernel has legitimate numerical differences from its padded/batched path.
- **Single-sample no-op negative control.** Explicit test (not just a parametrize case) analogous to the batch axis's own no-op check baked into `tiled_rematerialize`/`tiled_rematerialize_compute` (`batch <= 1` check, L304/L348): call `packed_seq_tiled_rematerialize_compute` with a one-sample `cu_seqlens` and assert (a) the output is bit-identical to calling `fn` directly (not just numerically close — no tiling machinery should have run), and (b) `PackedSeqTiledRematerializeCompute.apply` was never invoked (patch/spy the class, or check a call counter), so a future change cannot silently start tiling a non-packed row.
- **Distributed tile-count agreement, `world_size=2`.** `class TestPackedSeqTiledRematerializeDistributedAgree(DistributedTest)` with `world_size=2` (mirrors `TestTiledRematerializeDistributedReduce`, L586-627): give each rank a different `cu_seqlens` (different sample counts / lengths) that would produce different unmerged local tile counts; assert both ranks execute the same `agreed_count` iterations (instrument via a counter in the tile loop or by asserting `ds_grad_is_ready` flips True exactly once per rank) and that gradients match a single-rank packed-untiled reference computed outside the distributed test.
- **Cache-key isolation.** One assertion (can live inside the agreement test above or standalone) that two consecutive calls with *different* packings on the same rank do not reuse a stale agreed count — i.e. that this path is genuinely uncached, unlike `_agree_rematerialize_shards`'s `_agreed_shard_counts` dict (L85, L94-95). This guards against a future "helpful" caching change reintroducing the hang the WRITEUP warns about.

## Benchmark/measurement plan

Frame every claim as the peak decomposition from `WRITEUP_tiled_remat_intuition.md`: **floor + store + FFN workspace + mixer workspace**. `TiledMLP` already owns FFN; offload already owns store; this plan's only target is mixer workspace at packed `mbs=1`. Do not scale the intuition writeup's measured mbs-slope numbers (14.3 GiB mixer / 1.8 GiB FFN per extra microbatch, Qwen3.5-4B @ 32k) into a claimed packed-sequence slope — those are batch-axis measurements at `mbs>1`, not a mixer-only `mbs=1` sequence-length slope, and the intuition writeup itself warns against exactly that ("Do not scale the 14.3/1.8 mbs-slope as if it were a measured mixer-only `mbs=1` sequence slope"). Any packed-`mbs=1` slope this plan produces is new data, to be measured, not derived from the existing numbers.

The claim is **capacity**, not throughput: a packed `mbs=1` row that OOMs today in mixer rematerialization should fit after tiling, at some tok/s cost from extra Python-level forward/backward calls per tile. Per the WRITEUP's own bar, treat **>5% slower than packed `mbs=1` gc** as a regression to investigate, not an automatic pass — but do not compare this against batch-tiled `mbs>1` tok/s at all; that comparison already favors `mbs=1`+GAS in this project's existing measurements (`WRITEUP_tiled_remat_intuition.md`'s closing section: "`mbs=1` plus GAS already matches or beats tiled `mbs>1` on throughput") and re-litigating it here would conflate two different axes.

**Harness gap — checked, and it does not exist today.** `autorun/bench_qwen3_offload.py` has no packed/varlen input path:

- Input generation is a single dense `[mbs, seqlen]` random tensor (`ids = torch.randint(0, cfg.vocab_size, (mbs, seqlen), ...)`, line 964) with no `cu_seqlens`, no reset `position_ids`, no packing of multiple shorter samples into one row.
- `_install_tiled_rematerialize` (lines 228-316) wraps the *whole decoder layer* forward (`_is_text_decoder_layer(mod)`), classifying every kwarg with the existing batch-axis `classify_rematerialize_kwarg` — it would need a sibling installer that instead wraps only the attention/GDN submodule (mixer-only, per Scope) and calls `packed_seq_tiled_rematerialize_compute` with `cu_seqlens` threaded through, not `classify_rematerialize_kwarg`'s two-bucket system.
- The underlying kernel path is not the gap: the installed stack (`transformers==4.57.6`, confirmed on the pod) already supports packed sequences generically through `transformers/modeling_flash_attention_utils.py`'s `flash_attention_forward` — it derives `cu_seq_lens_q/k` and `max_length_q/k` from reset `position_ids` via `prepare_fa_kwargs_from_position_ids`, or accepts them directly as `FlashAttentionKwargs`. `bench_qwen3_offload.py` already sets `cfg.attn_implementation = "flash_attention_2"` (line 774), so the varlen kernel is reachable; the bench just never constructs a packed batch or threads reset `position_ids`/`cu_seq_lens_q/k` through the model call to trigger it. Qwen3's own `modeling_qwen3.py` has no packing-specific code of its own — it forwards `**kwargs` down to the shared flash-attention path, so no model-side change is needed beyond making sure those kwargs survive the decoder-layer `**kwargs` plumbing (the same `**kwargs` that `_install_tiled_rematerialize`'s `tiled_forward` wrapper already binds and re-splits with `inspect.signature`, lines 253-273).

What step 6 (bench plumbing) needs to add, concretely: a `--packed_seq` flag plus a way to specify a pack shape (e.g. `--pack_lens 4096,4096,8192` for one row of three samples, or a simpler `--pack_samples N --pack_len_avg L` for a synthetic uniform pack) that builds `input_ids`, reset `position_ids`, and `cu_seqlens` for one packed row instead of the current dense `[mbs, seqlen]` tensor; a `--packed_tiled_remat_shards`/`--packed_tiled_remat_budget` flag pair analogous to `--tiled_rematerialize_shards`/a new token-budget flag; and a new `_install_packed_seq_tiled_rematerialize(model, ...)` installer that finds and wraps the attention (or GDN) submodule specifically rather than `_is_text_decoder_layer`'s whole-layer match.

Primary measurement, once the harness gap above is closed: CUDA max allocated at fixed packed-row token count, `TiledMLP` on, comparing (i) packed `mbs=1` gc, no mixer tiling — OOMs or high peak on a packing this plan targets; (ii) packed `mbs=1` with `packed_seq_tiled_rematerialize_compute` wrapping the mixer, sweeping the token budget. Report peak, not tok/s, as the headline number, with tok/s reported alongside as a "did we regress more than 5%" check per the WRITEUP's bar.

## Risks and open questions, ranked

1. **Cross-rank tile-count agreement correctness under adversarial packing.** The MIN-then-merge scheme in this plan is sound by construction (Section "Cross-rank tile-count agreement" above proves `agreed_count <= N_local` for every rank), but it is uncached and runs once per wrapped mixer call per microstep — for a deep model that is one all-reduce and one device sync per layer per step, on top of the existing batch-axis path's own per-layer collectives when both are active simultaneously (packed `mbs=1` tiling one microbatch's rows while a different microbatch in the same run uses batch-axis tiling would be unusual, but the two mechanisms are not mutually exclusive at the code level and nothing currently prevents both from firing in the same step). This needs a real multi-rank measurement (step 4's test, then the bench harness once step 6 lands) before trusting the collective count is acceptable at production layer counts (Qwen3-scale models are 30-90+ layers).
2. **The kwarg allowlist may be incomplete for a real model.** The WRITEUP's allowlist (`cu_seqlens`, `cu_seq_lens_q/k`, `max_seqlen_q/k`, `max_length_q/k`, `seq_idx`, `position_ids`, sequence-major `attention_mask`) was written from the HF `FlashAttentionKwargs` shape this plan confirmed exists in `transformers==4.57.6`, but GDN-family models (the other named mixer, alongside attention) may carry additional pack-aware kwargs (e.g. a conv-state reset mask) that this plan has not read code for — the WRITEUP itself says GDN packing is legal "only if recurrent and short-conv state already reset at every document boundary — require and verify per model, do not assert." Step 6 (real model integration) is where this allowlist gap would surface, and it is the step most likely to require a follow-up commit to `classify_packed_kwarg`.
3. **GDN numerics under tiling may differ from packed-untiled, not just from unpacked.** Even granting that GDN already resets state at document boundaries in the packed-untiled baseline (a precondition this plan assumes but does not verify, per risk 2), splitting a packed row into tiles at *different* boundaries than a full single-tile pass could still expose an existing bug in how that reset state is threaded across a mixer call boundary if the state carrying mechanism is not itself boundary-aware in the same way `cu_seqlens` is — this plan's correctness oracle (Test plan, "Packed-vs-unpacked oracle" and the packed-tiled-vs-packed-untiled parity test) is designed to catch this, but only once a real GDN model is available to test against; the `PackedSeqMix` test module in steps 3-4 is a synthetic stand-in and cannot exercise real GDN state-reset code.
4. **Bench harness plumbing (step 6) is the largest unverified step.** Everything in steps 1-5 is self-contained and unit-testable without a real model; step 6 is the only place this plan's design meets an actual HF model's kwarg names and a real varlen kernel, and it is where the allowlist (risk 2) and any layout assumptions about `hidden_states` (`[1, T, H]` vs `[T, H]`, Section "Per-tile execution") get their first real-model test. Sizing this as its own commit (rather than folding it into steps 1-4) is deliberate so that a plumbing surprise there does not block landing the tested, reviewable core mechanism.
